# Agent、Cell 与原生 Core

本文说明 MRW 的嵌入 Agent 如何把自由对话转换为受项目、会话、权限和效果约束的领域操作。总体对象关系见[架构总览](../../../docs/architecture/README.md)，安装与使用见[使用说明](../../../docs/usage.md)。

## 1. 设计主张

Agent 不是与业务系统并列的第二套数据入口。它是一次研究工作流中的交互能力：Codex Core 负责理解、计划和调用，Cell 负责把一次调用绑定到当前项目、会话、已解析能力、具体工具参数和必要批准，原领域服务继续拥有写入、副作用和事实。

这一构造有三个直接结果：

1. **自由表达保持开放。** 用户不需要先填写业务表单或选择固定意图；项目、会话和附件身份等派生输入仍须有可追溯来源。
2. **能力可组合，权威不转移。** Skill 提供方法和成果要求，Tool 提供可执行入口，Facility 提供运行设施；三者都不能替代原领域服务。
3. **成功必须有读回。** 模型回答、工具已调用、请求已受理、领域已提交和结果可再次读取是不同事实。只有原执行者的持久结果才能证明领域操作完成。

## 2. 参与对象

| 对象 | 责任 | 不承担 |
| --- | --- | --- |
| Codex Core | 读取上下文、选择 skill/tool、形成调用和继续循环 | 领域写入、权限授予、结果认证 |
| Cell | 解析并固定本轮环境，绑定项目、会话、工具与参数，执行权限和效果合同 | 替代领域 writer，生成第二份事实 |
| Tool | 提供已注册的可执行操作和类型化输入输出 | 从目录可见推导出已授权或已执行 |
| Skill | 提供方法、适用情境和局部成果要求 | 绕过宿主权限或直接写库 |
| Facility | 连接数据库、工作流、存储或外部运行设施 | 成为新的领域事实 owner |
| 领域服务 | 执行授权、事务、持久化、领域判断和读回 | 把模型输出直接当成提交成功 |
| Codex WebUI | 承载对话、线程、文件交互和宿主能力 | 用界面状态替代 MRW 持久事实 |

项目限定作用范围，不授予权限。来源、材料、知识、证据、文档、运行和任务仍由各自服务写入；同一原文被多个项目收录时，项目级标注、可搜范围与研究成果不能因此合并。

## 3. Cell 的组成

一次已解析的 Cell 环境包含：

- 原生 Core 的会话和续接身份；
- 当前项目与可信 host actor；
- 已激活注册包及其内容摘要；
- 已解析的 skill 正文、版本摘要和适用范围；
- 已挂载工具及其 schema、权限和原执行入口；
- 设施绑定、项目范围和允许的效果；
- 本轮消息、附件、工作参数和读回引用。

只读 `GET /api/v1/agent-cell` 返回当前项目下按 package identity 解析出的惰性环境描述和摘要。它用于核对实际装配，不启动 Core，不执行工具，也不产生领域写入。

宏注册包、工具目录和系统投影是声明与观察入口。声明可见、包已激活、工具已挂载、参数已绑定、用户已批准、执行已提交，是不同阶段的事实，不能用前一项替代后一项。

## 4. 一次交互的边界

宿主通过 `/api/v1/agent-macro-host` 完成以下交接：

1. `prepare` 在项目内解析包、skill、tool 和设施，返回一次性 binding。
2. `bind` 将 binding 固定到 Codex thread；后续调用只能使用该线程已绑定的项目和环境。
3. `record-input` 记录用户输入和 admission，并把本轮上下文写入原会话服务。
4. `prepare-turn` 固定本轮可调用能力和续接规则。
5. `confirm` 记录用户对精确工具调用的批准或拒绝；未批准的动作不进入执行。
6. `dispatch` 校验线程、回合、工具、参数、项目、actor 和批准，再调用原工具执行者。
7. `end-turn` 结束本轮上下文，之后不得复用该回合的调用许可。

宿主 API 使用服务端密钥，并只接受可信 actor。本机单用户模式只对真实 loopback、无转发头且服务端密钥匹配的请求投影稳定 `local_host`；其他入口继续使用现有认证。项目、线程、回合、工具和批准任一不匹配都应拒绝，而不是选择最近会话或回退到其他项目。

## 5. Skill、Tool 与 Facility 的关系

Skill 与 Tool 是不同对象。Skill 正文提供方法和成果规定；Tool 提供真实调用入口；Facility 提供工具运行所需设施。一个 skill 可以引用多个 tool，一个 tool 也可以服务多个方法，但引用关系不自动产生授权。

环境解析至少核对：

- 注册包与激活记录属于同一项目；
- skill 路径位于允许根内，正文摘要与声明一致；
- tool 名称和 schema 与已挂载入口一致；
- facility 绑定属于当前项目和允许范围；
- 激活来源是 host policy 或真实人工批准；
- 不运行、不可运行的包不进入可执行环境。

工具调用继续使用原执行者的权限、事务、错误和读回合同。Cell 不建立第二套 writer，不复制工具返回为领域事实，也不把 metadata 注册当成工具已挂载或效果已完成。

## 6. 系统投影

`agent_runtime.system.inspect` 从 MRW 系统根对象出发，按需展开职责、对象、关系和工具目录。投影用于让 Agent 发现“系统里有什么、由谁负责、从哪个原入口读取或执行”，不替代领域查询。

投影遵循有界分页和稳定 revision：同一轮查询使用同一 revision，过期页返回可恢复错误，不能把截断结果当成完整系统。工具可见不等于可调用；最终执行仍经过 Cell 和原工具合同。

## 7. 输入、附件与项目

用户输入保留原话；Agent 生成的查询、筛选条件或工具参数是派生输入，必须能回溯到原消息、附件和项目。

附件在进入模型前需要有稳定身份、项目归属、内容摘要和可读回位置。把本机路径字符串当作附件内容、只在前端内存保留附件，或用文件名推断项目，都不能构成可信输入。纯附件回合与文字回合使用同一 admission、绑定、权限和结果读回路径。

切换项目只影响新线程；在途工作继续持有发起时的项目和能力快照。归档项目停止新的绑定、写入和执行，已有成果仍可读取、追溯和导出。

## 8. 权限、批准与失败

审批必须绑定精确的工具、参数、项目和动作摘要。批准一个动作不能授权同名的其他调用，也不能因线程已存在而跳过本轮确认。

失败保持原语义：

- 能力未配置、未挂载、无权限和不可用分别返回；
- 未知提交结果先按原操作读回；有副作用且无法确认时停止，不自动重放；
- 只读或已证明幂等的操作才可按原合同重试；
- 部分成功、待批准、取消、预算耗尽和领域失败不能被包装成完整成功；
- Cell 不可用时返回具体恢复路径，业务服务不得静默改走 provider 直连。

## 9. 不变量

| 不变量 | 可观察要求 |
| --- | --- |
| 原话与派生输入可区分 | 原消息保留，工作参数有来源 |
| 项目身份不被导航状态替代 | 每次绑定和执行都有明确项目 |
| 工具身份精确 | namespace、tool、schema 和参数一致 |
| 权限在执行处有效 | 未授权、未挂载或过期批准被拒绝 |
| 领域 owner 保持 | 写入由原服务完成，Cell 不生成第二事实 |
| 效果与读回分离 | 调用成功不自动等于持久结果成功 |
| 失败可恢复 | 类型化失败、重试边界和未知结果处理明确 |
| 生命周期可终止 | 回合结束、项目归档和取消停止后续执行 |

## 10. 当前验证边界

当前代码已有环境解析、内容摘要、注册读取、宿主绑定、输入记录、审批、工具派发、系统投影和领域读回入口，并有对应单元与合同测试。真正上线仍需在同一候选上验证：

- 宿主 OAuth 与本机单用户身份；
- 真实 Cell 项目绑定、纯附件回合、批准和原执行；
- Codex Core 的实际工具回调与多轮续接；
- 服务重启后的会话、批准和未完成操作语义；
- 领域写入后的持久读回、失败恢复和归档边界。

静态投影、注册检查或替身测试只证明各自输入范围，不能替代上述链路。
