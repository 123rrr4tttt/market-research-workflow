# Typed Knowledge Organization Plan (2026-03-07)

> 日期：2026-03-07
> 范围：类型节点、归类体系、分册、双语化、专题聚类、质量分级
> 状态：主题主计划文档，用于冻结知识组织层的问题定义、边界和第一阶段建议

## 1. 背景

当前平台已经具备采集、抽取、检索、图谱、资源池等多条链路，但“知识如何被组织”这一层仍然是分散的：

- 文档和抽取结果已经存在，但缺少统一的“类型节点/专题节点/分册结构”。
- 自动分类能力已经在部分链路中出现，但主要服务于 site entry 或资源池场景，还没有提升为平台级知识组织能力。
- 图谱能表达关系，检索能返回内容，writing 能消费资料，但中间缺一层统一、稳定、可治理的知识组织层。

母文档 [`抽象规划.md`](../2026-03-07-%E5%90%8E%E7%BB%AD%E5%AE%89%E6%8E%92/%E6%8A%BD%E8%B1%A1%E8%A7%84%E5%88%92.md) 对这一层提出了明确的新要求：

- 创建类型节点，用于承载和归纳具体信息节点。
- 结合 `RAG + 检索 + LLM` 辅助归类和专题化组织。
- 细化文档质量分级。
- 支持子项目内分类、分册、按主题分册。
- 支持信息双语化。

因此，本主题不是在现有标签或抽取结果上继续打补丁，而是要定义平台的知识组织层。

## 2. 当前基线

### 2.1 抽取与文档管理基线

当前仓库中，与知识组织层最相关的已有能力包括：

- 现代前端文档与抽取结果入口：
  - `main/frontend-modern/src/pages/OpsPage.tsx`
- discovery 存储与抽取结果沉淀：
  - `main/backend/app/services/discovery/store.py`
- 项目管理与分类相关入口：
  - `main/frontend-modern/src/pages/ProjectsPage.tsx`

这些路径说明：

- 平台已经能够看到文档、抽取结果、搜索历史、部分分类相关任务。
- 但“抽取结果如何进一步沉淀为结构化知识层”仍然缺少统一方案。

### 2.2 分类与资源池基线

当前已有若干与分类相关的后端能力：

- 资源池自动分类：
  - `main/backend/app/services/resource_pool/auto_classify.py`
- 资源池统一搜索与解析：
  - `main/backend/app/services/resource_pool/unified_search.py`
  - `main/backend/app/services/resource_pool/resolver.py`
  - `main/backend/app/services/resource_pool/extract.py`
- 站点项与能力分类：
  - `main/backend/app/services/resource_pool/site_entries.py`
  - `main/backend/app/services/resource_pool/llm_validator.py`

这些能力说明当前仓库已经具备：

- 规则优先、LLM fallback 的分类思路。
- 面向来源与资源池的分类机制。

但仍未解决：

- 类型节点是否是资源池分类的延伸，还是独立知识层概念。
- 文档实体、抽取实体、图谱节点、专题聚类之间是否共用一个组织层。

### 2.3 图谱与写作消费基线

知识组织结果的下游已经存在明确消费方：

- 图谱：
  - `main/frontend-modern/src/pages/GraphPage.tsx`
  - `main/backend/app/services/graph/*`
- writing / 报告：
  - `main/backend/app/services/writing/*`
  - `main/backend/app/api/llm_report.py`

这意味着知识组织层不是一个独立存档功能，而是后续图谱、写作、报告的中间层。

## 3. 核心问题定义

本主题必须解决以下四个结构性问题：

### 3.1 缺少一等公民的知识组织对象

当前平台有文档、抽取结果、图谱结果，但“类型节点”“专题节点”“分册对象”不是稳定的一等对象。没有一等对象，就无法建立：

- 稳定的归类规则
- 稳定的人工校正入口
- 稳定的消费接口

### 3.2 分类、分册、专题聚类、双语化混在一起

这些需求都合理，但它们不属于同一层：

- 分类更偏结构归属
- 分册更偏组织/视图形态
- 专题聚类更偏跨实体聚合
- 双语化更偏内容表达与消费能力

如果不先分层，主题计划会变成愿望清单。

### 3.3 自动归类缺少人工治理边界

当前仓库已经有 `auto_classify` 思路，但平台级知识组织不能完全依赖自动化。必须回答：

- 什么可以自动归类
- 什么必须人工确认
- 何时允许人工改写自动结果

### 3.4 知识组织层与图谱层边界不清

如果类型节点直接等同于图谱节点，本主题就会被图谱主题吞掉；如果完全脱离图谱，又会失去关系表达力。因此必须先冻结：

- 知识组织层负责定义什么
- 图谱层负责表达和编辑什么

## 4. 目标

本主题第一阶段要达成的目标是：

1. 定义知识组织层的核心对象集合。
2. 定义自动归类、人工校正、分册、专题聚类、双语化之间的关系。
3. 定义知识组织结果如何进入图谱、检索、写作、报告。
4. 给第一阶段能力边界一个可执行、可扩展的收敛版本。

## 5. 明确需求清单

以下需求来自母文档“各主题需求清单与阶段计划”，并结合当前仓库基线做了收敛。本主题后续细化不得跳过这些要求。

### 5.1 对象模型要求

- 必须定义三类核心对象之间的关系：
  - 类型节点
  - 普通信息节点
  - 专题节点
- 必须说明类型节点是否允许层级嵌套、是否允许多父归属、是否需要项目级隔离。
- 必须说明普通信息节点与现有文档、抽取结果、图谱节点之间的映射关系。

### 5.2 归类与治理要求

- 必须定义自动归类与人工治理的分工：
  - 哪些结论可以自动生成候选
  - 哪些结论必须人工确认
  - 哪些修改允许人工直接覆盖
- 必须定义最小归类主链：
  - 输入对象
  - 候选归类
  - 人工确认/修正
  - 回写组织层

### 5.3 分册、专题、双语化、质量分级要求

- 必须定义分册、专题聚类、双语化、质量分级分别落在哪一层。
- 必须说明它们是对象层、属性层还是消费视图层能力。
- 必须说明双语化服务的是同一知识对象的多语言表达，还是不同语言派生对象。
- 必须说明质量分级如何影响后续检索、图谱、报告或写作消费。

### 5.4 下游消费要求

- 必须明确知识组织结果如何进入：
  - 检索链路
  - 图谱链路
  - 报告链路
  - 写作链路
- 必须至少给出一个统一消费出口的最小约定，避免每个下游各读各的字段。

### 5.5 建设顺序要求

- 必须明确哪些能力属于“先建对象模型”。
- 必须明确哪些能力属于“后补自动化”。
- 第一阶段不得在对象模型未冻结前先写重自动化方案。

## 6. 范围

本主题当前纳入范围：

- 类型节点的职责与层级。
- 具体信息节点与类型节点之间的关系。
- 专题聚类与分册之间的结构关系。
- 自动归类与人工校正的分工。
- 质量分级和双语化在知识组织层中的位置。

### 5.1 第一阶段优先范围

第一阶段建议只冻结以下五项：

1. 类型节点的最低定义。
2. 信息节点归属与专题归属的关系。
3. 自动归类 + 人工确认的最小闭环。
4. 分册对象的最小语义。
5. 下游消费接口的最小约定。

## 7. 非目标

本主题当前不纳入：

- 直接重写 ingest 来源扩张方案。
- 在首轮文档中锁死数据库 schema。
- 承担图谱编辑交互和图谱回写合同。
- 把所有双语内容生产流程一次性定稿。
- 把所有专题类型枚举一次性列完。

## 8. 关键能力拆解

### 7.1 Type Node Layer

需要先回答：

- 类型节点是什么
- 它是否允许层级嵌套
- 它与普通信息节点、专题节点、标签的区别是什么

第一阶段建议把类型节点视为“知识组织层对象”，而不是直接视为 UI 标签或图谱可视化元素。

### 7.2 Classification Workflow

分类流程至少要分成三段：

1. 候选归类生成
2. 人工确认或校正
3. 组织层落盘与下游可见

当前 `resource_pool/auto_classify.py` 已经说明平台具备规则优先、LLM fallback 的能力，但平台级知识组织还需要更明确的人工治理点。

### 7.3 Booklet and Topic Layer

“分册”和“专题聚类”不应被视为同义词：

- 分册更像面向项目/主题的组织容器
- 专题聚类更像跨文档、跨节点的聚合视图

计划文档必须写清：

- 哪一个是主结构
- 哪一个是消费视图
- 两者如何互相引用

### 7.4 Quality and Bilingual Layer

质量分级与双语化都不是附属能力，而是知识组织层的两个约束维度：

- 质量分级决定知识能否被优先消费
- 双语化决定知识能否跨语言进入报告、检索或工作台

它们应该是知识对象的属性层，而不是完全独立的系统。

## 9. 阶段计划

### Phase 1：冻结对象层级和归类主链

本阶段目标是先把知识组织层“定义出来”，而不是先把自动化做重。

必须完成：

- 冻结类型节点、普通信息节点、专题节点三类对象的关系。
- 冻结分册、专题、质量分级、双语化的层级归属。
- 冻结自动归类 + 人工确认的最小闭环。
- 冻结至少一个统一下游消费接口样例。

本阶段不应做：

- 大规模专题枚举
- 重型 schema 迁移
- 复杂自动分类策略堆叠

### Phase 2：补自动归类、人工校正、质量分级

本阶段目标是让组织层开始具备可运营性。

必须补齐：

- 自动归类候选生成规则
- 人工确认、人工修正、人工覆盖的操作语义
- 质量分级输入来源和更新规则
- 归类结果进入检索/图谱/报告的基础生效机制

本阶段要重点控制：

- 自动化只产出候选，不越权替代治理
- 质量分级不能脱离对象层独立漂浮

### Phase 3：补双语化、专题聚类、分册协同消费

本阶段目标是把组织层从“内部结构层”推进到“跨场景消费层”。

必须补齐：

- 双语化对象策略
- 专题聚类与类型层的协同规则
- 分册对象如何服务写作、报告、图谱和检索
- 更完整的专题化消费能力

本阶段不应牺牲：

- 对象模型稳定性
- 下游消费接口一致性

## 10. 依赖与边界

### 8.1 与 `ingest-digestion-and-long-cycle-automation` 的边界

- ingest 主题定义内容如何进入系统
- 本主题定义内容进入系统之后如何被组织

### 8.2 与 `graph-editing-and-reporting` 的边界

- 本主题定义结构
- 图谱主题定义这些结构如何被表达、编辑、同步、消费

### 8.3 与 `llm-service-and-agent-platformization` 的边界

- 本主题提出归类、双语化、专题提取的模型能力需求
- 模型服务层如何统一治理，不在本主题主导

## 11. 第一阶段建议

第一阶段不建议先谈“大而全知识图谱本体”，而应先把下面三件事做清楚：

1. 类型节点最小定义
2. 自动归类与人工确认最小闭环
3. 分册/专题/质量/双语化在同一对象模型中的位置

如果这三件事不冻结，后续所有图谱、报告、写作消费都会建立在不稳定对象之上。

进一步建议按以下顺序推进：

1. 先从现有 `OpsPage`、discovery/store、resource_pool/auto_classify 路径抽取真实对象。
2. 画出最小对象关系图，而不是先列功能列表。
3. 用一个项目内样例验证“对象定义 -> 人工治理 -> 下游消费”是否闭环。
4. 在样例稳定前，不展开更复杂的自动专题化和双语化。

## 12. 风险与待确认问题

### 10.1 风险

- 类型节点如果直接复用图谱节点模型，可能过早把知识组织主题锁进图谱实现细节。
- 如果自动归类先做强于治理规则，会让分类结果难以被长期维护。
- 分册、专题、标签、类型节点如果没有主次关系，会让用户心智失控。

### 10.2 待确认问题

- 类型节点是否允许多父级归属。
- 分册是否是实体对象，还是查询/展示视图。
- 双语化是写入同一知识对象，还是维护语言派生对象。
- 质量分级是否参与下游检索与报告排序。

## 13. 最小验证

- 至少定义一个“类型节点 -> 具体信息节点 -> 专题聚类”的最小样例。
- 至少定义一个“自动归类 -> 人工确认 -> 落盘”的最小流程。
- 至少说明知识组织结果如何被图谱或写作链路消费一次。
- 至少说明一个 Phase 1 完成时即可验证的对象样本和字段约定。
